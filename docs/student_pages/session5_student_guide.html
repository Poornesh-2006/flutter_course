State Management with Riverpod

With setState, data lives inside one screen, and every other widget that needs it has to receive it through constructors. Today you learn Riverpod, which keeps shared data in providers that any widget on any screen can read and update directly.

By the end of today you can

Share state between screens with Riverpod, pick the right kind of provider, and keep your app's rules in a Notifier instead of inside widgets.

Riverpod 3 note

StateProvider moved to a separate import in Riverpod 3. If you see “StateProvider isn't defined”, add import 'package:flutter_riverpod/legacy.dart';. Many older tutorials and AI answers miss this.

Riverpod words, in plain English

Think of a classroom. With setState, the data is a note in one person's pocket: to reach anyone else, it has to be passed hand to hand. With Riverpod, the data is pinned on a notice board on the wall. Anyone can look at the board, and only the board's caretaker is allowed to change it.

The two rules

1. watch to show, read to change. In build(), always ref.watch. In onPressed and other callbacks, use ref.read. A widget rebuilds only if it watches something that changed.

2. Always give state a new value. Write state = [...state, item], never state.add(item). Riverpod only notices a new list or a new object.

Why setState breaks down

In demo 1 the cart lives in ShopScreen's State. Every widget that needs the cart, or needs to change it, must receive it through a constructor. This is called prop drilling. Some widgets take a parameter only to pass it on. Demo 5 builds the same shop with Riverpod.

Problems with the setState version:

  • Data and callbacks pass through widgets that don't use them.
  • When the cart screen changes the cart, both screens need extra setState calls to redraw.
  • The whole ShopScreen rebuilds for every change, even parts that didn't change.

A rebuild takes about a millisecond, so you can't normally see it. In demos 1 and 5, every widget shows a grey “built 1×” tag that counts its rebuilds and flashes yellow each time. In demo 1, tap ➕ on one product and all eight tags go up.

demo2

Setup: ProviderScope, ConsumerWidget and Provider

Nothing changes in demo 2. It shows where a shared value lives and how any widget reads it. Without Riverpod, you'd pass the app name down by hand:

// Without Riverpod: passed through every constructor
HomeScreen(appName: 'Campus Store')
  └─ _Footer(appName: appName)      // receives it again, and so on

With Riverpod, nothing is passed. _Footer() reads the name itself. Using Riverpod takes three steps.

// 1. Declare a provider at the top level of a file.
final appNameProvider = Provider<String>((ref) => 'Campus Store');

// 2. Wrap the app in ProviderScope. It stores every provider's value.
void main() => runApp(const ProviderScope(child: MyApp()));

// 3. Read it in a ConsumerWidget through `ref`.
class HomeScreen extends ConsumerWidget {
  @override
  Widget build(BuildContext context, WidgetRef ref) {
    final appName = ref.watch(appNameProvider);
    return Text(appName);
  }
}
  • Provider holds a value that doesn't change, or one calculated from other providers.
  • ConsumerWidget is a StatelessWidget with a ref. ConsumerStatefulWidget is the same for a StatefulWidget.
  • If you forget ProviderScope, the app throws Bad state: No ProviderScope found.
demo3

StateProvider, and ref.watch vs ref.read

StateProvider holds one simple value that can change, like a counter or an on/off switch.

import 'package:flutter_riverpod/legacy.dart';

final counterProvider = StateProvider<int>((ref) => 0);

// in build:
final count = ref.watch(counterProvider);

// in a button:
onPressed: () => ref.read(counterProvider.notifier).state++,

ref.watch

“Rebuild me whenever this value changes.”

Use it inside build() for anything you display.

ref.read

“Give me the value or notifier right now, once.”

Use it inside callbacks like onPressed to change state.

In the demo, replace ref.watch with ref.read on the commented line in build. The number stops updating on screen.

demo4

NotifierProvider for complex state

When state has several operations, such as add, toggle and remove, put them in a Notifier class. Widgets call its methods, and all the rules live in one place.

class TaskListNotifier extends Notifier<List<Task>> {
  @override
  List<Task> build() => [];             // the starting state

  void add(String title) {
    state = [...state, Task(title: title)];   // a NEW list
  }

  void remove(int id) {
    state = state.where((t) => t.id != id).toList();
  }
}

final taskListProvider =
    NotifierProvider<TaskListNotifier, List<Task>>(TaskListNotifier.new);

// in a widget:
final tasks = ref.watch(taskListProvider);               // the list
ref.read(taskListProvider.notifier).add('Revise Dart');    // call a method

State must be replaced, not changed

Riverpod only notices a change when you assign a new value to state. Changing the old list in place does nothing on screen.

state.add(task);                // ❌ same list, Riverpod sees no change
state = [...state, task];       // ✅ new list, widgets rebuild

task.isDone = true;             // ❌ fields should be final
task.copyWith(isDone: true)     // ✅ a new Task with one field changed

Derived providers

Don't store a value you can calculate. A Provider that watches another provider recalculates automatically:

final remainingCountProvider = Provider<int>((ref) {
  return ref.watch(taskListProvider).where((t) => !t.isDone).length;
});
demo5

Sharing state across screens

Demo 5 is the shop from demo 1, rebuilt with a cartProvider. The two apps look and work the same; only the inside is different.

// The caretaker: the only way to change the cart
class CartNotifier extends Notifier<List<String>> {
  @override
  List<String> build() => const [];                 // starts empty
  void add(String item) => state = [...state, item];
  void remove(String item) => state = [...state]..remove(item);
}
final cartProvider = NotifierProvider<CartNotifier, List<String>>(CartNotifier.new);

// Product tile: CHANGES the cart, never watches it, so it never rebuilds
onPressed: () => ref.read(cartProvider.notifier).add(name),

// Cart button: SHOWS the count, so it rebuilds when the cart changes
final count = ref.watch(cartProvider).length;

// Cart screen: shows the list AND removes items, with no callbacks passed in
final cart = ref.watch(cartProvider);
onPressed: () => ref.read(cartProvider.notifier).remove(item),
  • ShopScreen is a plain StatelessWidget. It holds nothing and passes nothing.
  • Remove an item on the cart screen and the badge on the shop screen updates by itself. There are no setState calls anywhere.

Errors you will see today

“Bad state: No ProviderScope found”Wrap your app in ProviderScope inside main().
StateProvider isn't definedRiverpod 3 moved it. Add import 'package:flutter_riverpod/legacy.dart';.
The screen doesn't update after calling a notifier methodYou changed the state in place (state.add(...)). Assign a new value: state = [...state, item].
The screen never updatesYou used ref.read inside build. Use ref.watch there.
ref.read(cartProvider).add(item) runs but nothing changesWithout .notifier you get the list itself, and add changes it in place. Call the notifier's method: ref.read(cartProvider.notifier).add(item).
“Undefined name 'ref'”The widget still extends StatelessWidget. Change it to ConsumerWidget and add WidgetRef ref to build.

Check yourself

What problem does Riverpod solve that setState doesn't?

It shares state between widgets and screens without passing data and callbacks through constructors, and it rebuilds only the widgets that watch the changed value.

When do you use ref.watch and when ref.read?

ref.watch inside build() for values you display. ref.read inside callbacks like onPressed to change state.

Provider, StateProvider or NotifierProvider: when do you use each?

Provider for read-only or calculated values. StateProvider for one simple value that changes. NotifierProvider for state with several operations and rules.

Why does state.add(item) not update the UI?

It changes the existing list, so state still points to the same object and Riverpod sees no change. Assign a new list instead.

What does ProviderScope do?

It stores the current value of every provider. Without it, no provider can be read.
