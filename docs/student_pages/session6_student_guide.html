Working with APIs

Until now, every piece of data in our apps was typed into the code. Today the data comes from the internet: you'll ask a server for it, turn the answer into Dart objects, and show the right screen while you wait, when it fails, and when there's nothing to show.

By the end of today you can

Fetch data from a web API with http, turn the JSON into typed model classes with fromJson, and show loading, error, empty and data states, including no internet and timeouts.

  • https://official-joke-api.appspot.com/random_joke: a random joke (project). Refresh the page and you get a new one.
Riverpod 3 note

When a provider fails, Riverpod 3 quietly retries it for about 30 seconds while showing the spinner. Our apps turn that off so the error message appears straight away: ProviderScope(retry: (retryCount, error) => null, child: ...).

The big picture: the waiter

An API is like a waiter. Your app doesn't walk into the kitchen (the server's database). It gives the waiter an order (a request to an address). The waiter comes back with a short answer (“here you go”, “we don't have that”, “the kitchen is on fire”) and a plate of data. The plate arrives wrapped as one long piece of text, so we unwrap it and put each item into a proper Dart box.

API words, in plain English

WordWhat it means
APIA web address that returns data instead of a web page.
Endpoint / URLThe exact address you ask, e.g. …/users/1. Different addresses give different data.
RequestYour app's question. GET reads data, POST creates, PUT/PATCH updates, DELETE removes. Today we only use GET.
Status codeA 3-digit answer to “did it work?”. 200 means yes.
BodyThe data in the response, always one long String.
JSONThe text format of the data. { } is one object (becomes a Map), [ ] is a list (becomes a List).
jsonDecodeTurns the JSON text into Dart Maps and Lists. Comes from dart:convert.
Model classA Dart class for one item, e.g. User with name and email.
fromJsonA constructor that builds one model object from one Map. Lets you write user.name instead of json['name'].
Future, async, awaitFrom Session 1: a value that arrives later. await waits for it without freezing the app.
.timeout(…)Give up after a set time instead of spinning forever.
FutureBuilderA widget that shows one thing while a Future is waiting and another when it's done.
FutureProviderThe Riverpod way: a provider that runs an async function and remembers the result.
AsyncValueWhat a FutureProvider gives you: loading, error or data, never more than one at a time.
.when(…)Asks you for one widget per state: loading, error, data.
ref.invalidate(p)Throw away the old result and fetch again. That's how Retry and “Next joke” work.

The concepts, in the order we cover them

demo1

http.get, status codes and jsonDecode

Two buttons: one asks for user 1 (status 200), the other for user 9999, who doesn't exist (status 404). The screen shows the raw body first, then the same data after jsonDecode.

import 'dart:convert';
import 'package:http/http.dart' as http;

final response = await http.get(Uri.parse('https://jsonplaceholder.typicode.com/users/1'));
response.statusCode   // 200
response.body         // '{"id":1,"name":"Leanne Graham",...}'  ← one long String

final Map<String, dynamic> json = jsonDecode(response.body);
json['name']                 // 'Leanne Graham'
json['address']['city']      // nested: one Map inside another
model

Model class with fromJson

Reading json['name'] everywhere is risky: one typo and the app crashes at runtime. A model class reads the JSON once, in one place.

// what the API sends (one user)
{
  "id": 1,
  "name": "Leanne Graham",
  "email": "Sincere@april.biz",
  "company": {
    "name": "Romaguera-Crona"
  }
}
class User {
  ...
  factory User.fromJson(
      Map<String, dynamic> json) {
    return User(
      id: json['id'] as int,
      name: json['name'] as String,
      email: json['email'] as String,
      company: json['company']['name']
          as String,
    );
  }
}

The API sends a list of users, so decode it as a List and turn each Map into a User:

final List<dynamic> data = jsonDecode(response.body);
return data.map((item) => User.fromJson(item)).toList();
errors

Turning every failure into a sentence

Four things can go wrong. Catch each one and throw a message a user understands. This is in users_api.dart:

try {
  final response = await http.get(url).timeout(const Duration(seconds: 10));
  if (response.statusCode != 200) {
    throw ApiException('The server answered ${response.statusCode}. Please try again.');
  }
  ...
} on TimeoutException {          // took longer than 10 seconds
  throw ApiException('The server took too long to answer...');
} on http.ClientException {      // no Wi-Fi / no data / server unreachable
  throw ApiException('No internet connection...');
} on FormatException {           // the body wasn't valid JSON
  throw ApiException('The server sent data we could not read.');
}
states

The four states every loading screen needs

loadingWaiting for the server. Show a spinner.
⚠errorSay what went wrong in plain words, and offer Retry.
∅emptyIt worked, but there's nothing. Say so kindly.
≡dataShow the list.

Demos 2 and 3 have Break and Empty switches in the AppBar, so you can see the error and empty states without switching off the Wi-Fi.

demo2

FutureBuilder

late Future<List<User>> _usersFuture;

@override
void initState() {
  super.initState();
  _usersFuture = fetchUsers();     // start the request ONCE, here
}

FutureBuilder<List<User>>(
  future: _usersFuture,
  builder: (context, snapshot) {
    if (snapshot.connectionState == ConnectionState.waiting) return Spinner();   // loading
    if (snapshot.hasError) return ErrorView(snapshot.error);                       // error
    final users = snapshot.data ?? [];
    if (users.isEmpty) return Text('No users found.');                           // empty
    return ListView.builder(...);                                                // data
  },
)

Never call fetchUsers() inside build(). build runs many times, and each run would send a new request. Start it in initState and keep the Future in a field. Retry calls setState with a new Future.

demo3

FutureProvider and AsyncValue

The same screen, the Riverpod way. No StatefulWidget, no initState, no Future in a field: the provider remembers the result.

final usersProvider = FutureProvider<List<User>>((ref) {
  return fetchUsers();
});

// in a ConsumerWidget:
final usersAsync = ref.watch(usersProvider);     // AsyncValue: loading OR error OR data

return usersAsync.when(
  loading: () => Spinner(),
  error: (error, stackTrace) => ErrorView(
    message: error.toString(),
    onRetry: () => ref.invalidate(usersProvider),   // fetch again
  ),
  data: (users) => users.isEmpty ? Text('No users found.') : ListView.builder(...),
);
  • .when makes you write all three. Forget one and it won't compile.
  • ref.invalidate(usersProvider) throws away the old result and fetches again.
  • Pull to refresh: RefreshIndicator(onRefresh: () => ref.refresh(usersProvider.future), ...).
  • The provider watches the Break and Empty switches, so flipping a switch fetches again by itself.

Errors you will see today

Spinner forever, and the request is sent again and againYou called the fetch function inside build(). Start it in initState, or use a FutureProvider.
“type 'List<dynamic>' is not a subtype of type 'Map<String, dynamic>'”The API returned a list [...] and you treated it as one object {...}, or the other way round. Open the URL in a browser and check the first character.
“type 'Null' is not a subtype of type 'String'” inside fromJsonA key is misspelled, or the value is nested one level deeper (like company.name).
“ClientException: Failed to fetch” in ChromeWrong address, http:// instead of https://, or an API that doesn't allow browsers. Today's APIs all work in Chrome.
The error screen takes about 30 seconds to appearRiverpod 3's automatic retry. Add retry: (retryCount, error) => null to ProviderScope.

Practice task (in class)

Homework: extend the Joke App

Check yourself

What do status codes 200, 404 and 500 mean?

200: it worked. 404: not found. 500: the server broke.

Why must the fetch not be called inside build()?

build() runs many times. Each run would send a new request, and the screen would keep reloading.

What are the four states of a loading screen?

Loading, error, empty and data.

What does fromJson do, and what happens if a key is misspelled?

It builds one model object from one JSON Map. A misspelled key gives null, so the app crashes at runtime with a “Null is not a subtype” error.

What does ref.invalidate(jokeProvider) do?

It throws away the current result and runs the provider again, which fetches a new joke.
