Returning a result from a screen

Navigator.push returns a Future. If you await it, your code waits until the next screen closes. That screen sends a value back with Navigator.pop(context, value).

Order
Selected size: L
await Navigator.push(…) → ← Navigator.pop(context, 'L')
Choose a size
S
M
L ←tap
XL
final chosen = await Navigator.push<String>(
  context,
  MaterialPageRoute(builder: (context) => const SizeScreen()),
);
if (!mounted) return;        // the screen may be gone after an await
if (chosen == null) return;   // user pressed back
setState(() => _size = chosen);
  • If the user presses the back arrow, the result is null. Always handle that case.
  • After an await, check mounted before you use context or call setState.

Named routes

Instead of building a MaterialPageRoute every time, give each screen a name in one place and navigate by name.

class AppRoutes {
  static const home = '/';
  static const profile = '/profile';
}

MaterialApp(
  initialRoute: AppRoutes.home,
  routes: {
    AppRoutes.home: (context) => const HomeScreen(),
    AppRoutes.profile: (context) => const ProfileScreen(),
  },
)

Navigator.pushNamed(context, AppRoutes.profile, arguments: 'Priya');

// inside ProfileScreen:
final name = ModalRoute.of(context)!.settings.arguments as String;
  • Keep route names as constants. A typo then becomes a compile error instead of a crash.
  • arguments has no type, so you have to cast it. For passing data, constructors are safer.
demo5

setState() and how rebuilds work

Changing a variable does not change the screen. setState changes the value and tells Flutter to run build() again so the screen shows the new value.

// ❌ value changes, screen does not
_count++;

// ✅ value changes and build() runs again
setState(() => _count++);

In the demo, tap “+1 without setState” three times. Nothing changes on screen. Then tap “+1 with setState” and the number jumps by four. The console also shows that const widgets are not rebuilt.

StatefulWidget lifecycle: initState and dispose

createStateonce→ initStateonce · set up→ buildmany times→ disposeonce · clean up

A StatefulWidget is split into two classes. The widget itself (SecondsCounter) only describes what to show and is recreated often. Its State object (_SecondsCounterState) holds the values that change, like _seconds, and stays alive while the widget is on screen. createState() is where Flutter makes that State object. You never call it yourself.

@override
State<SecondsCounter> createState() => _SecondsCounterState();

In the demo, “Remove counter” destroys the State object. “Add counter” calls createState() again and makes a new one, which is why the count starts again from 0.

@override
void initState() {
  super.initState();          // super FIRST
  _timer = Timer.periodic(...);  // start things here
}

@override
void dispose() {
  _timer.cancel();              // stop things here
  super.dispose();             // super LAST
}

Anything you start in initState (timers, controllers, listeners) must be stopped in dispose. Otherwise it keeps running after the widget is gone, and you get setState() called after dispose().

TextField and TextEditingController

A TextEditingController lets your code read, change and clear the text in a TextField.

final _nameController = TextEditingController();

TextField(
  controller: _nameController,
  decoration: const InputDecoration(labelText: 'Your name'),
  keyboardType: TextInputType.name,
)

_nameController.text      // read what the user typed
_nameController.clear()    // empty the field

@override
void dispose() {
  _nameController.dispose();   // always dispose controllers
  super.dispose();
}
  • keyboardType picks the keyboard: phone, emailAddress, number.
  • obscureText: true hides a password.
  • onChanged runs on every keystroke. onSubmitted runs when the user presses Done.

Form, TextFormField and validators

A Form groups fields together. A GlobalKey<FormState> gives you a handle on the form, so one call can check every field.

Phone98765
Phone number must be 10 digits
Emailravi@example.com
final _formKey = GlobalKey<FormState>();

Form(
  key: _formKey,
  child: TextFormField(
    validator: (value) {
      if (value == null || value.isEmpty) return 'Enter a phone number';
      if (value.length != 10) return 'Phone number must be 10 digits';
      return null;   // null means valid
    },
  ),
)

// on Save:
if (_formKey.currentState!.validate()) {
  // every field is valid
}
  • A validator returns null when the value is fine, or an error message when it isn't.
  • validate() runs every validator, shows the messages, and returns true only if all fields pass.
  • autovalidateMode: AutovalidateMode.onUserInteraction re-checks a field while the user types.

Errors you will see today

The number doesn't change on screenYou changed a variable without setState.
“setState() called after dispose()”A timer or listener is still running after the widget was removed. Cancel it in dispose, and check mounted after every await.
“Null check operator used on a null value” at currentState!You forgot key: _formKey on the Form.
The result is always nullThe screen called Navigator.pop(context) without a value, or the user pressed back.
“type 'Null' is not a subtype of type 'String'”You opened a named route without arguments, but the screen casts them to a String.
“Navigator operation requested with a context that does not include a Navigator”You used the context of the widget that builds MaterialApp. Navigate from a screen inside home: instead.

Homework: extend the Contact Book

Check yourself

How does a screen send data back to the screen that opened it?

It calls Navigator.pop(context, value). The screen that opened it receives the value from await Navigator.push(...).

What does await Navigator.push(...) give you if the user presses back?

null. That's why you check for null before using the result.

What happens if you change a variable without calling setState?

The variable changes, but build() doesn't run, so the screen keeps showing the old value.

Why must you dispose a TextEditingController?

It holds resources and listeners. If you don't dispose it, it stays in memory after the screen is gone.

What should a validator return when the value is valid?

null. Any String it returns is shown as the error message.
